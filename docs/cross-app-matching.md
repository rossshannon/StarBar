# Cross-app matching: a Spotify song in the user's Music library

Measured 2026-10-28 on macOS 27.2 with Music 1.7.2, against one user's library of 8,092 tracks (8,089 of them songs), read-only. These are the facts the matching in StarBar 1.8 is built on: `SongName`, `SongMatcher`, `MusicLibraryIndex` and `LibraryMatchFinder`. Re-measure before relying on anything here for a different Music version or a very different library.

## What Spotify gives to match on

From `com.spotify.client.PlaybackStateChanged` (see [spotify.md](spotify.md)):

- `Artist` is **one name**, the primary artist. Featured artists appear in `Name` ("Song (feat. Someone)"), never in `Artist`.
- `Album Artist` is always empty for a song.
- `Duration` is in milliseconds.
- `Track ID` tells a song (`spotify:track:`) and a local file (`spotify:local:`) from an episode. Only those two are looked for.

So the library side is the one that gets split into names: a Music credit like "Calvin Harris & Dua Lipa" has to match a Spotify `Artist` of "Calvin Harris".

## Reading the library

- **One property over the whole library is one Apple Event**: `arrayByApplyingSelector:` on the library playlist's tracks returns every track's value in order. 14 to 48 ms per property on 2026-10-28, ten properties in about 250 ms. The Swift overlay in Xcode 16.4's SDK has no `arrayByApplying(_:)`, so the index calls the selector through the Objective-C runtime.
- **But the time varies a great deal.** On 2026-10-29 the same read of eleven columns of the same library took about 0.35 s, 4.4 s and 25 s at three launches of StarBar a few minutes apart. Music answers Apple Events one at a time, so while the read is out every other read StarBar makes waits behind it. So the index reads only what finding a song takes (persistent ID, name, artist, album artist), and `LibraryMatchFinder` reads the rest (media kind, album, length, rating, plays) from the few copies a song has. Each column's time is logged; what made the slow reads slow is not known.
- The lists come back in the same order, so they are paired by position. A track added or removed between two reads would pair one song's name with another's ID, so the persistent IDs are read first and again last, and the read is thrown away if they differ.
- **A missing value is left out of the list, not kept as a placeholder.** Measured 2026-10-29 on 8,093 tracks: `duration` came back with 8,090 values, because three songs (all file tracks) had no length, while JXA's own bulk read of the same property keeps a placeholder for each. Paired by position, every length after the first gap would have belonged to the song before. So the columns a song needs (persistent ID, name, artist) must be full length or the read is thrown away, and any other short column is left out of that read. The first build on a real library threw every read away for this reason; the tests' fakes had full columns.
- **Music can be slow to answer after a spell idle.** Measured 2026-10-29: the persistent-ID search for one copy, under StarBar's 1 s short timeout, failed with errAETimeout (-1712) on its count event after Music had been idle for about seven minutes; the same search from JXA straight afterwards took 209, 65, 16, 11 and 26 ms. Scripting Bridge answers a timed-out search with an empty list, which looks like a song that has gone, so a lookup has to count the failed events to tell the two apart. The copies are therefore read on the index's background connection with its 10 s timeout, and a lookup Music didn't answer is asked again once.
- **Where the time between a Spotify song starting and its copy's stars goes.** Measured 2026-10-29 with "Go Slowly" by Radiohead played four times over: three starts took 332 to 587 ms from Spotify's notification to the match, of which reading the copy on the index's connection took 153 to 421 ms and fetching it again on the station's connection, on the main thread, about 150 ms more. The fourth took 3,940 ms. Music answered that lookup's events in 496, 16, 17, 157, 424, 691, 716, 285 and 281 ms, against its usual 15 to 25, the station's fetch took 848 ms for seven events, and the main thread had just spent two seconds on two menu bar reads that timed out (errAETimeout, -1712). Of the sixteen events a lookup sent, eight found Music's library playlist, four on each connection, and the menu bar and strip then read the copy's rating and heart on the main thread, four events each. Since then the playlist is found once per Music process on each connection, the rating and heart are read with the copy, and the station's track is a reference that sends nothing.
- **One record, not one event per property.** The first build after that still read seven properties one at a time, each through the persistent-ID search, so each event searched the library again. Installed and measured the same night, with two Radiohead songs played alternately in Spotify, one copy took 993, 2,089, 459 and 1,359 ms, starting two minutes after the live tests had kept Music busy for two minutes; both Go Slowly reads missed the 1 s wait, so it showed as a Spotify song first. Eleven minutes later, with Music idle, the same build read six copies in 122 to 200 ms, and every play showed the copy's stars directly, in the menu bar and the strip, 130 to 211 ms after Spotify's notification. So most of the first run's time was Music still being slow, not the reads themselves. A probe a few minutes later, with Music idle, timed the ways of reading the same two copies four times each: the seven reads through the search took 133 to 172 ms; `get()` on the search (7 to 22 ms) and then the seven reads by ID took 121 to 172 ms; `get()` and then one read of `properties` took 34 to 91 ms (258 ms once, the first time). The record has 59 properties, among them everything a copy needs except `ratingKind`, which has to be read on its own. The media kind arrives as an enumerated descriptor (`'kMdS'`), the heart as a boolean `NSNumber`. Reading rating and heart through the station's search reference took 15 to 65 ms. That build read a copy as a `get()` and a `properties` read, plus `ratingKind` when it has a rating.
- **Reading `location` makes Music announce a library change, so a copy is read one property at a time.** The `properties` build, installed the same night, read a copy in 48 to 80 ms, but from the first match on it read the whole library and the copy again every 3 s, 20 times a minute, for as long as the song played: each read was followed by "Music's library changed" about 2.5 s later. A probe with osascript against one library copy, 20 s apart with Spotify paused and Music otherwise idle, found the cause: the name through the search, the eight properties one at a time on the resolved reference, and `rating kind` each set off nothing; `location` on its own and the `properties` record (59 items, `location` among them) each set off two notifications, 2.8 s and 14.7 s later. The track was an Apple Music download, and its `location` an alias to a `.movpkg` package; its modification date did not change. A matched AAC file's `location` (“Analogue” by A-ha, an `.m4a`) set off nothing, so the live test's first cut, which read only the library's first track, passed with the bug put back; it now reads one song of each iCloud status it finds. So a copy is a `get()` on a search that checks persistent ID, name and artist together, then the media kind, album, rating and heart one at a time, the rating's kind only for a rated copy, and the length and plays only when there are copies to choose between. `MusicLibraryLookupTests.testReadingACopyAnnouncesNoLibraryChange` listens for an announcement after a read. On that library its sample of one song per iCloud status took six songs, one of them an Apple Music download (“Suddenly” by Billy Ocean, kind “HLS media”); with a `location` read put back for that song, it failed with a change at 2.9 s. Two songs in the sample were shared tracks, which have no `location`, and one file track's `location` read failed with -1728, so a bug put back as a `location` read on every copy shows as “Music didn't answer” instead, and `iTunesFileTrack.location`, declared as a non-optional `URL`, traps on a nil answer. Installed and measured the same night with Music idle, alternating the same two songs three times each: no library change from install to a minute after the last play, copies read in 85 to 122 ms, and the stars drawn 92 to 129 ms after Spotify's notification. The first play after launch took 975 ms: 588 ms to read the library, 158 ms for the copy, and 214 ms on the main thread for the station to find Music's library playlist, five Apple Events it makes once per Music process.
- **The first library read after a launch can fail.** Measured 2026-10-29: 66 s after StarBar launched, the first read, for the first Spotify song, failed with -1701 (errAEDescNotFound) in 14 ms, before any column was read, and the song showed Spotify's heart to its end though it was in the library; the next read, 8 s later, found all 8,093 songs in 599 ms. The cause is not known. A failed read while Music runs is now asked again, like a copy read Music didn't answer.
- Rejected: a `whose` query per song (8 to 18 ms, but one per field combination and no fuzzy matching), Music's `search` command (matches word prefixes, ignores accents, but treats `'` and `’` as different, and Music 1.7.2's `only` enumeration has `names`, not `songs`), and the iTunesLibrary framework (an entitlement and a privacy prompt).
- Music's `whose` ignores case, accents and `'` against `’`. A compound `whose` with `_and` fails from JXA but works from AppleScript.

## What the library looks like

These decided the rules more than any guess did.

| | Count |
|---|---|
| Titles shared by different artists | 397 |
| Songs held in both a studio and a live or remix version | 75 |
| Songs held two or more times | 442 |
| ... of which the copies' ratings disagree | 103 |
| Credits a comma, `&`, "and" or `+` would split into one-word names, as "Earth, Wind & Fire" | 52 |

- Titles shared by different artists are why the artist must match: title alone would rate the wrong song.
- Studio against live or remix is why those words are kept, so the two count as different songs. That is a choice, not a measurement, and can be revisited.
- Duplicates with conflicting ratings are why one copy is chosen, by a fixed order (the album Spotify named, then a rated copy, then the nearest length, then the most played), and only that copy is rated (also a choice: rating every copy was the alternative).
- Those one-word splits are why a comma, `&`, "and" or `+` splits a credit only when one of the resulting names has more than one word. The first version split them all, and "Earth" alone matched. The cost is a duo of one-word names ("Simon & Garfunkel" and any real pair like it) matching only on the whole credit.
- **A track on a live or remix album often says so only in the album's name.** "Everything In Its Right Place" on "I Might Be Wrong: Live Recordings", the whole of Nirvana's "MTV Unplugged In New York", and Spotify's "Foregone Destruction" on "Tournament Rematch: Unreal Tournament Remixed", which is someone else's remix credited to the original composer. So an album's name can mark its tracks live or remix too (`SongName.albumVersions`), and two copies match only when title and album together say the same. Of the 736 pairs of library tracks the title rules call the same song, this tells 26 apart, 22 rightly. The other four come from albums that only sound like it ("I Could Live In Hope" by Low, "Giant (Remixes)", which holds the original too) and each costs one copy where the user has another. "Live" in an album's name counts only before "at", "in", "from" or "on", after a bracket or at the end, because albums are often named after songs: "Live to Tell", "Live Forever". The index holds no albums, so this is checked once each copy's album has been read (`SongMatcher.ranked(_:for:)`).

## Recall against the user's Spotify likes

Measured 2026-10-29 by running the rules (through the Python mirror in the project's shared files) over the 185 songs liked in the user's Spotify account and the 8,092-track library read the day before. The likes are 183 different songs. **18 are found**; the other 165 were checked for near misses.

- 20 were found by name; the album rule then left out two, both from "Tournament Rematch: Unreal Tournament Remixed", which had matched the original recordings, 122 s and 48 s shorter. Those two are why the album rule exists.
- Most of the rest the user doesn't have: game and film soundtracks, covers, and songs by artists the library has other songs by.
- **Three songs the user has were missed because the two apps credit them to different names**: "The Merchant" by Yoann Laulan is the library's by Valmont de Ragondas, his alias; "Orsis" by Peter McConnell is the library's by Blizzard Music; "Curry Goat, Rice and Peas" by Autotuned Vids is the library's by "Autotunedvids & Solesky". Matching on title and length alone would find all three (their lengths agree within a second) but was rejected: in the same library 19 pairs of tracks share a title and a length within 1.5 s with no artist in common, and of the 12 that aren't voice memos several are covers, such as "Killing Me Softly" by the Fugees and by Roberta Flack, 1 s apart.
- **Length is not a test of the same recording either**: some matches differ greatly in length and are still the same song in another edit ("Sweet Harmony", 4:22 on the single and 15:18 on the album), and within the library 112 same-song pairs differ by more than 30% and 10 s, many of them radio or single edits ("Move On Up" is 2:46 and 8:49).
- "a-ha" and "Aha" fold to different names ("a ha" against "aha"). None of the likes is affected, since the one a-ha like is an acoustic version the user doesn't have.

## Rules from the first review

Four reviews of the first build, 2026-10-29, ran real titles through the matcher and found these matching another recording. Each is now a rule with a test in `SongNameTests` or `SongMatcherTests`.

- "Stay (with Justin Bieber)" by The Kid LAROI found Bieber's own "Stay". A guest never counts as the artist on their own, on either side.
- "Strobe - Michael Woods Remix" found "Strobe (Sebastien Leger Remix)", and "Clocks - Live in Sydney" would find "Clocks (Live at Glastonbury 2011)". A named version matches only the same name, or a track whose album's name holds it.
- "Rock of Ages - Re-Recorded" found the original, "re" and "recorded" both being edition words. A re-recording is now a version.
- "Yesterday (With Strings)" found the Beatles' "Yesterday", and a bare "feat" cut "A Feat of Strength" to "A". Someone credited with "with" must be credited on the other side, and a bare featured credit needs its dot.
- "AC/DC" split into "ac" and "dc". A slash now splits only like a comma.
- "Intro" by The xx on *Coexist* (60 s) found the "Intro" on *xx* (127 s). A length rule was tried first and replaced after the second review (below).
- With seven or more copies, which six were read came down to persistent IDs. All copies are now read, up to twelve; past that, see the second review.

## Rules from the second review

The same reviewers, on the fixes above, 2026-10-29. Three of those fixes brought problems of their own, and the length rule cost more than it saved.

- "Live at Wembley 1986" matched "Live at Wembley 1987", and "Take 1" matched "Take 2": a version's name dropped its numbers. Numbers now stay in it; a remaster's year ("- 2011 Remaster") is taken out first.
- Plain "Clocks" on *Live in Sydney* matched plain "Clocks" on *Live in Buenos Aires*. Two performances neither title names (live, remix, acoustic, demo, session, re-recording, orchestral) are now the same recording only on the same release: the albums once their edition words and Music's " - Single" or " - EP" are off. An instrumental or a reprise is the same on any album.
- Spotify's "Hotel California - Live On MTV, 1994" missed the "(Live)" on *Hell Freezes Over*, because a named version needed the name in the other's album. A version one side names now also matches a plain one on the same release. "Recorded Live at Wembley" now names Wembley, and "Live 2003" is a live album.
- "Queen & David Bowie" no longer found Queen's "Under Pressure": only names of more than one word were kept from a split credit. Every name is kept again, once the split itself has been allowed. "Metro Boomin, The Weeknd & 21 Savage" lost The Weeknd, because ", The" was always joined to the name before it; a credit is now read both ways.
- **The length rule went.** It lost "Sweet Harmony" (4:22 against the album's 15:18), radio edits that don't say so and singles, and still let "Intro" at 131 s match one at 127 s. Instead a title that names a part of an album ("Intro", "Interlude 2", "Untitled", "Skit") must be on the same release. Chosen on 2026-10-29. Length now only orders copies, and is read only when there are copies to choose between.
- "One - Live" with thirteen studio copies of "One" in the library went over the twelve read and found nothing. Past twelve, only the copies whose titles mark the same kinds of recording as Spotify's are read; still too many is no match. Reading copies also has a 10 s deadline in all.
- A slow Music showed a 4-star copy as unrated, since a failed read answers 0, and Rate Up then saved 1 star. A read Music didn't answer is now ignored: the stars stay, or what was last read of the copy comes back. A slow Music also counted as a deleted copy, refusing the first click; only Music saying the copy has gone counts now. The rating shortcuts check the copy as a click does, and a rating just chosen holds over a read that comes back before Music has it, as the heart already did.
- The first song after a launch showed Spotify's heart before its stars, the matcher taking 420 ms to build from nothing. The first wait is now 2 s, and each track's credits are worked out once.
- Known misses kept: " x " splits "Lil Nas X & Billy Ray Cyrus" after "Nas"; "Title - Subtitle - Remastered 2011" keeps its remaster; "Live After Death" and "Live and Dangerous" don't read as live albums.

## Rules from the third review

The same reviewers, minus one, on the second round's fixes, 2026-10-29. Each is a rule with a test.

- **What counts as one release was too loose and too strict at once.** "Tour Anthology (Live in Sydney 2003)" and "(Live in Buenos Aires 2017)" were one release, since the brackets came off with the edition words, so plain "Clocks" on one matched plain "Clocks" on the other. And "I Might Be Wrong: Live Recordings" was not "I Might Be Wrong", nor "Coexist (Tour Edition)" "Coexist". The release is now the album without its edition words, an edition the rules don't know by its last word or its bonus tracks, Music's " - Single", and a plain version, bracketed, after a dash or as a subtitle. A version the album names stays, and so does a subtitle that is no version: "TRON: Legacy" is not "TRON".
- On one release, "Live On MTV, 1994" and "Live on MTV" didn't match, a named version needing the same name on both sides. On the same release one name may now say less than the other.
- Johnny Cash's "Folsom Prison Blues" from the 1st Show matched the one from the 2nd Show, on the same Legacy Edition: ordinals were dropped as edition words. Ordinals now stay with numbers. An anniversary ("25th Anniversary") and a record's size ("12\" Remix") go, and "2003 Digital Remaster" goes whole. A year beside a remaster can be the performance's: "Live at Glastonbury 2011 Remastered 2020" is Glastonbury 2011, not plain Glastonbury.
- "Bob Dylan & The Band" found The Band's own "Tears of Rage", once every name of a split credit was kept. A one-word name is kept only when it leads the credit, which keeps Queen's "Under Pressure" and makes "Metro Boomin, The Weeknd & 21 Savage" a known miss for a song Spotify credits to The Weeknd.
- James Horner's "Main Title" on *Braveheart* would match the one on *Aliens*. A film score's cues ("Main Title", "End Credits", "Opening Titles") are now generic titles, as are titles made of two generic parts ("Intro (Skit)") and Roman numerals ("Interlude II"). "Theme", "Finale" and "Opening" are not, being songs' names too.
- Past twelve copies, the copies read were chosen by Spotify's title alone, so a song on a live album found the studio copies. They are now chosen by title and album together. Known limit: a plainly titled copy on a live album isn't read for a Spotify title that says "Live"; the copy read in its place is the same recording.
- **A held rating or heart ended early.** A read Music didn't answer fell back to what was on screen, and that matched the held choice, so the hold ended and the next read, still Music's old value, put the old stars back. The hold is now `HeldChoice`, which only Music's own answer can end by agreeing. A write Music refuses also ends it, so the re-read after a refusal shows Music's value.
- What was last read of a copy didn't know about a rating chosen since, so a later fall-back to it showed the old stars. A choice now updates it. The strip uses it only when Music doesn't answer, never as Music's answer, or its own hold would end.
- The 10 s deadline was only checked between copies, so one more 3 s event could pass it. Each event's timeout is now cut to what is left.
- Known misses added: "P*U*L*S*E" and other albums named with symbols were not tried; a click while Music isn't answering sends its write on the main thread at the default timeout, as a click on Music's own song already does.

## Open

- Recall against the user's likes is above; recall against what they actually play has not been measured. The first live checks, 2026-10-29: three versions of "The Maker" by Daniel Lanois each got the right answer. The studio version found the user's studio copy on Sling Blade, "The Maker - Live" found their "The Maker (Live)" on the same live album, and "The Maker - Calypso Demo" found nothing, the word "demo" keeping it from the studio copy. Seven songs the user doesn't own were correctly not found.
- The names-only read, on the third review's install, 2026-10-29: the first song after a launch took 1,832 ms from the question to the answer, with the matcher built in about 163 ms; the next five took 85 to 124 ms. One launch is not a measure of how reliably quick it is.
- No rating has been written through this path to a real library yet.
